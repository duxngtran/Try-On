## 1. Mô tả

**Là** User, **tôi muốn** tải lên 1 ảnh chân dung toàn thân chuẩn và nhập chiều cao/cân nặng **để** hệ thống dùng làm mẫu khi tạo ảnh tôi mặc thử sản phẩm (Epic 3).

## 2. Actors

| Actor | Mô tả |
|---|---|
| User (role `user`) | Xem, cập nhật hồ sơ của **chính mình** |
| Hệ thống | Frontend → Backend (Express) → Supabase Postgres (số đo) + Supabase Storage (ảnh, bucket private) |
| Admin | **Không** xem/sửa hồ sơ hay ảnh của user ở sprint 01 |

## 3. Phạm vi

| Trong phạm vi (Must) | Ngoài phạm vi sprint 01 |
|---|---|
| Xem hồ sơ của mình | Kiểm tra tự động bằng AI ảnh có phải toàn thân / đúng tư thế |
| Tải lên / thay thế 1 ảnh toàn thân | Cắt, xoay, chỉnh sửa ảnh trên trình duyệt |
| Nhập / sửa chiều cao, cân nặng | Nhiều ảnh mẫu, chụp ảnh trực tiếp bằng camera trong app (ngoài input file mặc định của mobile) |
| Đồng ý cho phép xử lý ảnh (consent) | Giới tính, số đo 3 vòng, size áo/quần |
| Xóa ảnh (Should) | Xóa toàn bộ tài khoản |

## 4. Định nghĩa "hồ sơ đầy đủ"

`profileCompleted = true` khi **đồng thời** có: ảnh toàn thân hợp lệ, chiều cao, cân nặng. Đây là điều kiện để vào Phòng thử đồ (US-05). Backend tính giá trị này và trả về trong `GET /api/auth/me` và API hồ sơ.

## 5. Luồng chính

### 5.1 Xem hồ sơ
1. User (đã đăng nhập) mở trang **Hồ sơ** (sau đăng ký được chuyển tới đây tự động).
2. Frontend gọi API lấy hồ sơ. Backend trả chiều cao, cân nặng, trạng thái consent, `profileCompleted` và **signed URL** ngắn hạn của ảnh (nếu có).
3. Giao diện hiển thị:
   - Ảnh hiện tại hoặc ô trống kèm **hướng dẫn chụp ảnh chuẩn** (mục 5.4) và ảnh minh họa đúng/sai.
   - Form chiều cao (cm), cân nặng (kg).
   - Nếu hồ sơ chưa đầy đủ: banner "Hoàn thiện hồ sơ để bắt đầu thử đồ" liệt kê phần còn thiếu.

### 5.2 Tải lên / thay thế ảnh
1. Lần đầu tải ảnh, User phải tích ô đồng ý: *"Tôi đồng ý cho Try-on lưu trữ và sử dụng ảnh này để tạo ảnh thử đồ, bao gồm việc gửi ảnh tới dịch vụ AI xử lý ảnh."* Chưa tích thì nút chọn ảnh bị khóa.
2. User chọn ảnh (trên mobile: chọn từ thư viện hoặc chụp bằng camera qua input file).
3. Frontend kiểm tra sơ bộ định dạng, dung lượng, kích thước, tỉ lệ (mục 7.1); hiển thị **xem trước** cùng checklist tự kiểm tra (đứng thẳng, thấy từ đầu đến chân, một người, nền đơn giản…).
4. User bấm **Lưu ảnh**. Frontend gửi `multipart/form-data`, hiển thị tiến trình tải lên; nút bị khóa trong lúc gửi.
5. Backend:
   1. Xác thực JWT; chỉ thao tác trên hồ sơ của `sub` trong token.
   2. Kiểm tra consent đã được ghi nhận (lưu thời điểm đồng ý ở lần đầu).
   3. Kiểm tra lại toàn bộ quy tắc mục 7.1, xác định định dạng thật bằng nội dung file (magic bytes), không tin tên file/MIME do client gửi.
   4. Chuẩn hóa ảnh: xoay theo EXIF orientation, **xóa toàn bộ metadata EXIF** (GPS, thiết bị), thu nhỏ nếu cạnh dài > 2048 px, lưu dạng JPEG.
   5. Tải lên bucket private với tên file do server sinh ngẫu nhiên (không dùng tên file gốc).
   6. Cập nhật đường dẫn ảnh trong hồ sơ; sau khi cập nhật DB thành công mới **xóa file ảnh cũ** (nếu có).
   7. Trả về hồ sơ mới kèm signed URL.
6. Frontend hiển thị ảnh mới, thông báo "Đã cập nhật ảnh", cập nhật `profileCompleted`.

### 5.3 Nhập / sửa chiều cao, cân nặng
1. User nhập Chiều cao (cm) và Cân nặng (kg), bấm **Lưu thông tin**.
2. Frontend validate (mục 7.2); backend validate lại và cập nhật.
3. Thông báo "Đã lưu thông tin", cập nhật `profileCompleted`.
4. Ảnh và số đo lưu **độc lập** (lưu số đo không bắt buộc phải có ảnh và ngược lại).

### 5.4 Hướng dẫn ảnh chuẩn (hiển thị trên giao diện)
- Một người duy nhất, đứng thẳng, nhìn thẳng, tay buông xuôi hoặc hơi tách khỏi thân.
- Thấy rõ toàn thân từ đỉnh đầu đến bàn chân, không bị cắt.
- Ảnh dọc, đủ sáng, nền đơn giản, không vật cản phía trước cơ thể.
- Mặc đồ ôm vừa người (tránh áo khoác dày, váy rộng).

### 5.5 Xóa ảnh (Should have)
1. User bấm **Xóa ảnh** → hộp thoại xác nhận "Ảnh sẽ bị xóa vĩnh viễn và bạn sẽ không thể dùng phòng thử đồ cho đến khi tải ảnh mới."
2. Backend xóa file khỏi Storage và xóa đường dẫn trong hồ sơ; `profileCompleted = false`.

## 6. Luồng lỗi

| # | Tình huống | HTTP | Mã lỗi (`error.code`) | Thông báo hiển thị |
|---|---|---|---|---|
| E1 | Chưa đăng nhập / token hết hạn | 401 | `UNAUTHORIZED` / `TOKEN_EXPIRED` | Chuyển về Đăng nhập (US-01) |
| E2 | Chưa đồng ý consent mà gửi ảnh | 400 | `CONSENT_REQUIRED` | "Vui lòng đồng ý điều khoản sử dụng ảnh trước khi tải lên." |

| E4 | Sai định dạng (kể cả đổi đuôi file) | 400 | `INVALID_FILE_TYPE` | "Chỉ chấp nhận ảnh JPG, PNG hoặc WEBP." |
| E5 | Vượt dung lượng | 413 | `FILE_TOO_LARGE` | "Ảnh tối đa 10 MB." |
| E6 | Độ phân giải quá thấp | 400 | `IMAGE_TOO_SMALL` | "Ảnh cần tối thiểu 512 × 1024 px." |

| E11 | Tải lên Storage thành công nhưng cập nhật DB lỗi | 500 | `INTERNAL_ERROR` | Như E10; backend xóa file mới vừa tải để không để lại file mồ côi |
| E12 | Mất mạng khi đang tải ảnh | — | — | "Mất kết nối, vui lòng thử lại." Giữ ảnh xem trước để gửi lại |
| E13 | Signed URL hết hạn khi đang xem trang | — | — | Frontend gọi lại API hồ sơ để lấy URL mới (không báo lỗi cho user) |
| E14 | Gửi quá nhiều lần tải ảnh | 429 | `TOO_MANY_REQUESTS` | "Bạn thao tác quá nhanh, vui lòng thử lại sau." |
| E15 | Cạnh dài > 8000 px (bổ sung ở bước 3) | 400 | `IMAGE_TOO_LARGE` | "Ảnh quá lớn, cạnh dài tối đa 8000 px." |
| E16 | Ảnh động (WEBP/PNG nhiều khung hình) (bổ sung ở bước 3) | 400 | `INVALID_FILE_TYPE` | Như E4 |

## 7. Quy tắc validation

Frontend kiểm tra để phản hồi nhanh; **backend kiểm tra lại toàn bộ** và là nơi quyết định.

### 7.1 Ảnh toàn thân

| Quy tắc | Giá trị |
|---|---|
| Số lượng | Đúng 1 ảnh / user; tải ảnh mới = thay thế ảnh cũ |
| Định dạng | JPEG, PNG, WEBP (xác định bằng nội dung file). Không nhận HEIC, GIF, SVG, ảnh động |
| Dung lượng | ≤ 10 MB (file gốc) |
| Độ phân giải | Chiều rộng ≥ 512 px **và** chiều cao ≥ 1024 px (tính sau khi xoay theo EXIF) |
| Kích thước tối đa | Cạnh dài ≤ 8000 px (chặn ảnh quá lớn gây tốn bộ nhớ); ảnh hợp lệ có cạnh dài > 2048 px được thu nhỏ còn 2048 px |
| Tỉ lệ | Ảnh dọc: chiều cao / chiều rộng trong khoảng **1,3 – 2,5** |
| Nội dung "chuẩn toàn thân" | **Không kiểm tra tự động** ở sprint 01. Dựa vào hướng dẫn (5.4) và checklist tự kiểm tra của user |

### 7.2 Chiều cao & cân nặng

| Trường | Kiểu | Khoảng hợp lệ | Bắt buộc khi lưu | Thông báo lỗi |
|---|---|---|---|---|
| Chiều cao | Số nguyên, đơn vị cm | 100 – 250 | Có | "Chiều cao phải từ 100 đến 250 cm." |
| Cân nặng | Số, tối đa 1 chữ số thập phân, đơn vị kg | 30,0 – 250,0 | Có | "Cân nặng phải từ 30 đến 250 kg." |

- Gửi cả 2 trường trong cùng một lần lưu; không chấp nhận giá trị rỗng, âm, chữ, `NaN`.
- Frontend chấp nhận cả dấu `,` và `.` làm dấu thập phân, gửi lên backend dạng số.
- Backend bỏ qua mọi trường ngoài danh sách (không cho sửa `user_id`, `role`, đường dẫn ảnh qua API này).

## 8. Acceptance criteria

**AC-01 — Xem hồ sơ trống sau đăng ký**
- *Given* user vừa đăng ký
- *When* mở trang Hồ sơ
- *Then* thấy ô tải ảnh kèm hướng dẫn, form chiều cao/cân nặng trống, banner "Hoàn thiện hồ sơ" và `profileCompleted = false`.

**AC-02 — Bắt buộc consent trước khi tải ảnh lần đầu**
- *Given* user chưa từng đồng ý consent
- *When* chưa tích ô đồng ý
- *Then* không chọn được ảnh; nếu gọi thẳng API tải ảnh thì nhận 400 `CONSENT_REQUIRED`.

**AC-03 — Tải ảnh hợp lệ**
- *Given* user đã đồng ý consent
- *When* tải ảnh JPG 3 MB, 1080 × 1920 px
- *Then* ảnh được lưu vào bucket private, metadata EXIF bị xóa, trang hiển thị ảnh mới qua signed URL.

**AC-04 — Thay thế ảnh**
- *Given* user đã có ảnh A
- *When* tải lên ảnh B hợp lệ
- *Then* hồ sơ trỏ tới ảnh B, file ảnh A bị xóa khỏi Storage.

**AC-05 — Giữ ảnh cũ khi tải lỗi**
- *Given* user đã có ảnh A
- *When* tải ảnh B thất bại (sai định dạng, quá lớn, lỗi Storage)
- *Then* hồ sơ vẫn hiển thị ảnh A và có thông báo lỗi tương ứng mục 6.

**AC-06 — Từ chối ảnh sai quy tắc**
- *Given* user đã đồng ý consent
- *When* tải lần lượt: file `.exe` đổi đuôi thành `.jpg`; ảnh 12 MB; ảnh 400 × 800 px; ảnh ngang 1920 × 1080 px
- *Then* nhận lần lượt `INVALID_FILE_TYPE`, `FILE_TOO_LARGE`, `IMAGE_TOO_SMALL`, `INVALID_ASPECT_RATIO`; không file nào được lưu vào Storage.

**AC-07 — Lưu chiều cao/cân nặng**
- *Given* user ở trang Hồ sơ
- *When* nhập chiều cao `165`, cân nặng `52,5` và bấm Lưu
- *Then* dữ liệu được lưu (165 cm, 52.5 kg) và hiển thị lại đúng khi tải lại trang.

**AC-08 — Từ chối số đo ngoài khoảng**
- *Given* user ở trang Hồ sơ
- *When* nhập chiều cao `90` hoặc `251`, hoặc cân nặng `25` hoặc `52.55`
- *Then* hiện lỗi dưới ô tương ứng; API trả 400 `VALIDATION_ERROR`; dữ liệu cũ không đổi.

**AC-09 — Hồ sơ đầy đủ**
- *Given* user đã có chiều cao và cân nặng hợp lệ
- *When* tải ảnh hợp lệ thành công
- *Then* `profileCompleted = true` (trong API hồ sơ và `GET /api/auth/me`) và banner "Hoàn thiện hồ sơ" biến mất.

**AC-10 — Ảnh không truy cập công khai**
- *Given* user đã có ảnh
- *When* bất kỳ ai truy cập đường dẫn public của file trong Storage, hoặc dùng signed URL đã quá hạn
- *Then* bị từ chối. Ảnh chỉ xem được qua signed URL còn hạn do backend cấp.

**AC-11 — Không xem được hồ sơ người khác**
- *Given* user X và user Y đều có hồ sơ
- *When* X dùng token của mình gọi API hồ sơ (bất kể truyền id nào)
- *Then* chỉ nhận/sửa được hồ sơ của X; API hồ sơ không nhận id user từ client.

**AC-12 — Xóa ảnh (Should)**
- *Given* user đã có ảnh
- *When* bấm Xóa ảnh và xác nhận
- *Then* file bị xóa khỏi Storage, hồ sơ không còn ảnh, `profileCompleted = false`.

## 9. Yêu cầu phi chức năng

### Bảo mật & quyền riêng tư
- Ảnh lưu trong **bucket private**; frontend không bao giờ nhận đường dẫn Storage thô hay key Supabase. Chỉ backend (service role key) đọc/ghi Storage và DB.
- Ảnh trả về frontend qua **signed URL hạn 15 phút** (cấu hình qua env).
- Đường dẫn file theo user id + tên ngẫu nhiên do server sinh; không chứa email, tên file gốc.
- Xóa EXIF (đặc biệt vị trí GPS) trước khi lưu.
- Chiều cao, cân nặng, đường dẫn ảnh không được ghi vào log, không nằm trong JWT, không trả về cho user khác hay cho Admin.
- Lưu thời điểm user đồng ý consent (bằng chứng đồng ý). Khi user xóa/thay ảnh, file cũ bị xóa thật khỏi Storage.
- Giới hạn tải ảnh: tối đa 10 lần / user / giờ; giới hạn dung lượng body ở tầng upload middleware để chặn file lớn trước khi xử lý.

### Hiệu năng
- Tải lên + xử lý ảnh 10 MB hoàn tất ≤ 5 giây (p95, không tính thời gian truyền mạng phía client).
- API lấy hồ sơ ≤ 500 ms (p95), bao gồm tạo signed URL.
- Lưu số đo ≤ 300 ms (p95).

### Usability
- Responsive (≥ 360px); trên mobile input file cho phép chọn thư viện hoặc camera.
- Có xem trước ảnh trước khi lưu, thanh tiến trình khi tải, thông báo lỗi tiếng Việt cụ thể (mục 6).
- Ô số dùng `inputmode="numeric"` (chiều cao) và `inputmode="decimal"` (cân nặng), hiển thị đơn vị cm/kg.

## 10. Dependencies

| Quan hệ | Story | Ghi chú |

| Phụ thuộc | US-01 | Cần đăng nhập; dùng middleware auth và `GET /api/auth/me` |

## 11. Đã xác nhận & ràng buộc

**Ràng buộc (đã chốt):** ảnh toàn thân và chiều cao/cân nặng là dữ liệu nhạy cảm → bucket private; frontend không gọi Supabase trực tiếp; mọi truy cập qua backend Express (D-02, D-03). Định nghĩa `profileCompleted` (D-09); lưu phiên bản/thời điểm ảnh cho cache Epic 3 (D-15).

**Đã xác nhận (người dùng duyệt 2026-11-04, xem `DECISIONS.md`):**
- A1 (D-11). **Không** kiểm tra tự động ảnh có phải toàn thân chuẩn; chỉ kiểm tra kỹ thuật (định dạng, dung lượng, độ phân giải, tỉ lệ dọc) + hướng dẫn + checklist tự kiểm tra.
- A2 (D-12). Mỗi user chỉ có 1 ảnh; ảnh cũ bị xóa vĩnh viễn khi thay thế (không lưu lịch sử).
- A3 (D-11). Không hỗ trợ HEIC; iOS Safari thường tự chuyển sang JPEG khi chọn ảnh qua input file. Nếu thực tế bị lỗi thì bổ sung sau.
- A4 (D-11). Ngưỡng ảnh (≥ 512 × 1024 px, tỉ lệ 1,3–2,5, ≤ 10 MB) chọn theo đầu vào phổ biến của các model virtual try-on (khoảng 768 × 1024). Có thể điều chỉnh khi chọn model GenAI ở Epic 3.
- A5 (D-13). Chiều cao, cân nặng chỉ dùng đơn vị cm / kg; khoảng hợp lệ 100–250 cm, 30–250 kg (người trưởng thành).
- A6 (D-10). Consent một lần cho việc lưu trữ và gửi ảnh tới dịch vụ AI; không có chức năng rút consent riêng ở sprint 01 (xóa ảnh là cách dừng sử dụng).
- A7 (D-14). Admin không xem được ảnh và số đo của user.
- A8 (D-08). Chưa thu thập giới tính hay số đo khác ở sprint 01.
